# Claude as the model (reference)

A worked example of running the whole pipeline **with no API**: Claude reads the emails and
documents and supplies the answers the model would have given. It was done on 2026-09-21, when the
free-tier Gemini quota was exhausted (HTTP 429) and every real run failed at classification.

It is a reference, not part of the app. It shows exactly what the pipeline asks a model, how little
of that is actually needed, and what a clean run on this dataset looks like.

## What it does

Only three functions are swapped, and nothing else in the pipeline changes:

| Replaced | By |
|---|---|
| `classify.call_json` | `answers/classify.json`, one entry per email |
| `extract.extract_fields` | the keyword parser's value where it is sure, else `answers/extract.json` |
| `extract._vision_extract` | `answers/extract.json`, read from the page image |

Document reading, Tesseract OCR with per-word confidence, validation, comparison and the
human-review rules are the project's own code. No network call is made.

The user's flow was: **OCR every email's documents, send only the failed or low-confidence ones to
the model, and send what the model cannot settle to a person.** That is what the ladder in
`app/pipeline/extract.py` already does; this run just made each step visible.

## Files

| File | What it is |
|---|---|
| `stage1_parse.py` | Stage 1. Parses all 250 attachments (OCR for scans, keyword parser for text). No model. Says which fields still need one. |
| `build_classify_answers.py` | Claude's classification rules, one per email wording. Writes `answers/classify.json`. |
| `build_extract_answers.py` | Claude's hand-read values for the 36 documents the parser could not fully read. Writes `answers/extract.json`. |
| `render_scans.py` | Saves the page image of each scan, which is what the vision step is shown. |
| `run_with_claude.py` | Runs the real pipeline with those answers. |
| `crosscheck.py` | Compares a run with another (default: `web/report.json`) on the emails that have documents. |
| `answers/*.json` | The answer sheets, generated by the two build scripts and kept so the run is reproducible. |

## Run it

From the repo root, with the virtual environment active and Tesseract configured in `.env`:

```bash
python reference/claude-as-llm/stage1_parse.py         # results/claude-llm/parsed.json
python reference/claude-as-llm/run_with_claude.py      # results/claude-llm/results.jsonl, output.json, ...
python reference/claude-as-llm/crosscheck.py           # agreement with web/report.json
```

By default everything goes to `results/claude-llm/` (git-ignored), so it cannot touch your real
results. `--into-results` writes to `results/` itself, like a fresh `POST /run`: the old
`results.jsonl` is copied to a `.bak` first if it holds a real verdict, then replaced. Restart or
reload the app to see it.

## What it found (the run of 2026-09-21)

**Stage 1, no model.** 250 documents: 242 text (192 txt, 22 xlsx, 8 docx, 20 PDFs with a text
layer), 6 scanned PDFs, 2 corrupt PDFs (`email_511` and `email_515`, BL). The parser resolved all 7
fields on **212 of 250** documents by itself.

**What the model was asked.** 520 classifications (nothing else can classify), 135 fields on 30
text documents (mostly PDFs whose labels sit on their own line, plus blank or placeholder values
such as `N/A`, `TBA` and `____MT`), and 42 fields on the 6 scans. Tesseract page quality on the
scans was 62 to 72 out of 100 and misread values (`297,750` for `237,750`, `HANITONG` for
`NANTONG`), so those went to the page image.

**Result.** 520 records, none failed: 367 OK, 45 mismatch, 108 needs review (96 attachment
missing, 10 missing value, 2 unreadable).

**Cross-check against Colt's earlier full run** (`web/report.json`), on the 126 emails with
documents: 122 identical, and all 45 of these mismatches are ones his run also found. The four
differences:

- `email_145`: a **real defect this run misses**. SI shipper `APRIL FINE PAPER TRADING`, BL shipper
  `APRIL FINE PAPER TRADING (MIDDLE EAST) FZE`. These are two distinct entities, but the "same
  party plus extra detail" rule in `compare.py` treats one as the other plus an address. The rule
  should probably be limited to address-like suffixes.
- `email_411`: every value matches, so the other run misread it.
- `email_516`, `email_517`: the SI has placeholders; this run returns `null`, so a person decides.

## Judgement calls, and limits

- **91 "please send the draft BL" emails** have no attachments. They are labelled `BL_COMPARISON`
  at 0.6 confidence because they sit in the same threads as the real BL checks, so the pipeline
  routes them to a person as "attachment missing". Labelling them `GENERAL` instead would cut
  those 96 review cases to about 5. It is one rule in `build_classify_answers.py`, and a rerun
  takes seconds.
- **`wrong_doc_type` is never produced.** The invoice, packing-list and certificate-of-origin
  "BL"s (`501` to `505`) come out as `missing_value`, because nothing in the pipeline checks what
  kind of document it was given.
- **This is not a general classifier.** The rules encode the wordings found in this inbox. A new
  kind of email matches no rule and `build_classify_answers.py` stops with an error, which is the
  point: it cannot silently mislabel.
- **The answers are one reading, not ground truth.** Use `crosscheck.py` against any other run
  before trusting a difference either way.
